Compatibilitat FP4 ↔ API (repo FemPinya/api)

L'API és la capa entre FP3 i l'app Flutter. Analitzem si FP4 pot substituir FP3 com a font de dades per a aquesta API, i quin esforç implica.

App Flutter
↔
FemPinya/api (L11 + API Platform)
↔
BD FP3 (mysql)
Arquitectura actual. La API no té BD pròpia — llegeix directament de FP3.

Migra bé

  • Events (nom, dates, adreça, tipus, visibilitat)
  • Perfil del casteller (alias, nom, cognoms)
  • Tipus d'event (1/2/3 ↔ training/performance/activity)
  • Auth via Sanctum (ja instal·lat a FP4)
  • Acompanyants a l'assistència

Necessita adaptació

  • Status assistència: numeric → string enum
  • Auth: api_users + pivot → Casteller directe
  • User context: casteller actiu i vinculats
  • Tags d'event: re-mapear IDs
  • boards_enabled: colla_config → settings JSON

Incompatible / pendent

  • Attendance options: JSON de tag IDs → event_answers (incompatible)
  • Rondes: taula no existent a FP4
  • Notificacions: sistema no existent a FP4
  • Public URL (pissarra): BoardEvent no implementat
  • Pissarra assignacions: Fase 3b no feta

Decisió arquitectònica recomanada

★ Opció A — API endpoints natius a FP4 (recomanat)
  • Sanctum ja instal·lat. Afegir rutes /api/v1/ a FP4 directament.
  • Elimina la dependència del repo FemPinya/api.
  • L'app Flutter adapta els nous endpoints (feina al costat Flutter).
  • Permet evolucionar l'API amb les noves funcionalitats de FP4 (preguntes, etc.).
Opció B — Adaptar FemPinya/api a FP4 DB
  • Canviar els models del repo api per llegir la BD de FP4.
  • Mantenir dos repos separats (api + fp4) = complexitat operacional.
  • Els DTOs i State Providers haurien d'adaptar els status mappings.
  • Risc: el repo api quedarà obsolet igualment quan FP4 tingui tots els endpoints.
